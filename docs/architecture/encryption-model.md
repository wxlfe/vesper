# Encryption Model

Vesper uses client-side end-to-end encryption so prayer request contents, personal prayers, and routine custom text are unreadable from Firebase Console, Cloud Functions, logs, analytics tooling, and operational dashboards.

## Core Requirement

Sensitive prayer content and user-supplied routine content must only exist in plaintext on trusted user devices. The backend stores encrypted payloads and routing metadata only.

## Threat Model

Vesper protects against:

- Firebase Console access exposing prayer contents
- Accidental plaintext logging on backend services
- Database exports revealing request bodies
- Database exports revealing personal prayer text or routine custom text
- Over-broad internal staff access
- Compromised notification payload history exposing private details

Vesper does not fully protect against:

- A compromised user device after local unlock
- A malicious group member who can legitimately decrypt group content
- A routine recipient who can legitimately decrypt intentionally shared custom text
- Screenshots or manual copying by authorized readers
- Metadata inference from timestamps, group IDs, membership, or activity volume
- A malicious client build distributed outside trusted app channels

## Cryptographic Standards

Recommended Flutter libraries:

- `cryptography`
- `sodium_libs`

Preferred primitives:

- XChaCha20-Poly1305 for authenticated symmetric encryption
- X25519 for public-key key agreement or sealed-box style key wrapping
- Ed25519 for signatures if message authenticity beyond AEAD is needed
- Secure random generation from platform cryptographic APIs

Avoid custom cryptography, custom key derivation, unauthenticated encryption, reused nonces, and hand-rolled serialization formats for signed or encrypted data.

## Key Hierarchy

```text
user keypair
  |-- public key stored in Firestore
  |-- private key stored only on device

group key
  |-- generated by creator/Leader device
  |-- encrypted once per group member
  |-- used to protect group-scoped administrative and legacy payloads

request content key
  |-- generated per prayer request on the creator device
  |-- used to encrypt one canonical request payload
  |-- wrapped separately for the request owner and authorized group members

user content key
  |-- generated or provisioned on trusted user devices
  |-- used to encrypt user-private prayer sessions, routine sections, and personal prayers
  |-- never stored as plaintext on the backend
```

## User Keypair

Each user device generates or imports a user keypair after authentication. The public key is uploaded to Firestore. The private key is stored only locally in iOS Keychain or Android Keystore-backed secure storage.

Private keys must never be stored in Firestore, transmitted to Cloud Functions, included in logs, included in crash reports, or sent through notification payloads.

## Group Encryption Key

Each group has a symmetric encryption key. The group key encrypts prayer request bodies, private comments, follow-up notes, pastoral notes, sensitive tags, and attachment metadata.

The group key is encrypted separately for each member using that member's public key. A user can read group content only if they have an active membership record and a decryptable `group_keys` document for the current key version.

## User-Private Content Key

Each user has key material for encrypting personal prayer sessions, routine sections, and prayer book entries. This key material must be available across the user's trusted devices without becoming backend-readable plaintext.

Recommended approaches:

- Device-based sync where an existing trusted device encrypts the user content key for a new device public key.
- Optional recovery passphrase in a later phase, with the content key backed up only as ciphertext.

The user content key encrypts private session names, custom routine text, personal prayers, and routine section labels. If reminder scheduling requires plaintext trigger metadata such as local time and timezone, keep that metadata minimal and never include prayer text in notification payloads.

## Encrypted Payload Format

Every encrypted document should include enough non-sensitive metadata to support decryption and migration.

```json
{
  "ciphertext": "base64",
  "nonce": "base64",
  "keyVersion": 3,
  "payloadVersion": 1,
  "algorithm": "xchacha20-poly1305"
}
```

Authenticated additional data should bind ciphertext to stable metadata such as document ID, group ID, collection name, key version, and payload version. This prevents encrypted payloads from being copied into a different context without detection.

## Prayer Request Encryption Workflow

Encrypting a private request:

1. Generate a random request content key on the creator device.
2. Serialize the sensitive request payload.
3. Encrypt the payload with the request content key and a fresh nonce.
4. Upload one canonical `prayer_requests/{requestId}` document containing ciphertext, nonce, key version, payload version, algorithm, owner ID, status, and timestamps.
5. Wrap the request content key to the creator's public key and store it in `request_key_grants/{requestId_userId}`.

Sharing a request to a group:

1. Confirm the creator is an active member of the target group.
2. Create `request_shares/{requestId_groupId}` with metadata only.
3. Load active group members and their public keys.
4. Wrap the same request content key separately for each active member.
5. Store one `request_key_grants/{requestId_userId}` document per recipient.

Decrypting a request:

1. Download encrypted request metadata and ciphertext.
2. Query `request_key_grants` for the current user's grant with `requestId == requestId` and `userId == currentUserId`.
3. Unwrap the request content key locally with the user's private key.
4. Decrypt the request payload locally.
5. Render plaintext without logging it or writing it to unencrypted storage.

For multi-group submission from the home request composer, create one canonical encrypted request and one share record per selected group. One request shared to two groups remains the same `requestId`; prayer actions aggregate by `requestId` across all groups. Do not upload plaintext or content-derived summaries for any request, share, key grant, action, report, notification, log, or analytics event.

When a new member joins a group, newly added group members should gain access to requests already shared to that group. Because the backend cannot unwrap request content keys, this backfill is Leader-only and client-driven: the approving Leader's device unwraps each request content key it can access, wraps it to the new member's public key, and writes the new encrypted grants. If grant backfill is incomplete, the member may temporarily see placeholders until a Leader retries.

## Personal Routine Encryption Workflow

Encrypting a private routine section or personal prayer:

1. Load the user's trusted local content key.
2. Serialize the sensitive routine or prayer payload.
3. Encrypt the payload with a fresh nonce.
4. Upload ciphertext, nonce, payload version, algorithm, and minimal non-sensitive metadata.

Decrypting private routine content:

1. Download encrypted session, section, or personal prayer metadata and ciphertext.
2. Resolve the user's local content key.
3. Decrypt locally.
4. Render plaintext without logging it or writing it to unencrypted storage.

Vesper must not ship prayer-book, lectionary, or denominational office text as built-in content. Any such text in the app is user-supplied and encrypted as user content.

## Shared Routine Encryption Workflow

When a user shares a routine, they intentionally share all routine sections. Custom text sections are shared with their content and placement. Request-feed sections are shared only as dynamic slots; they never include the sharer's request IDs, request content, or group-derived feed contents.

Shared routine content should be encrypted for intended recipients or transported through an app-level encrypted sharing mechanism. The backend must not receive plaintext custom text from shared routines.

## Membership Flows

### Group Creation

1. Creator creates group metadata.
2. Creator device generates a random group key.
3. Creator device encrypts the group key for the creator public key.
4. Firestore stores the group, creator membership, and creator encrypted group key.

### Group Invitation

1. An active member creates or shares a copyable invite code.
2. Invitee creates or signs into an account.
3. Invitee device generates a user keypair if needed.
4. Invitee public key is uploaded.
5. Invitee enters the invite code and creates a join request.
6. Leaders review who requested access and, when known, who invited them.
7. A Leader approves membership.
8. Leader device encrypts the active group key to the invitee public key.
9. Invitee downloads and locally decrypts their encrypted group key.

The server never receives the plaintext group key.

### Group Administration

Group administration uses a simplified Leader/Member model. Any Leader may approve join requests, promote Members, demote Leaders when another Leader remains, remove members, and remove inappropriate requests. These workflows do not require access to plaintext prayer content beyond what the Leader can already decrypt as a group member.

Administrative workflows must be protected by Firestore rules and, where Cloud Functions are used, server-side validation of current Leader status. Rules or backend validation must prevent removal or demotion of the last active Leader. Administrative audit events must contain metadata only and must not include prayer plaintext.

### Member Removal

When a member is removed, the group should rotate to a new group key for future content.

Recommended process:

1. Leader device generates a new group key.
2. Leader device encrypts the new key for remaining active members.
3. Firestore marks the new key version as active.
4. New content uses the new key version.
5. Removed member loses access to future content.

Historical content access revocation requires re-encrypting prior content. This is expensive and may be deferred based on retention policy.

## Account Recovery

End-to-end encryption makes account recovery a product and security tradeoff.

### Option 1: Device-Based Recovery

If the user loses all trusted devices, encrypted data is inaccessible and the user must rejoin groups. This is the simplest and strongest security posture.

### Option 2: Recovery Passphrase

The user creates an optional recovery passphrase. The private key is encrypted with a passphrase-derived key and backed up server-side as ciphertext. This improves usability but adds implementation complexity and weakens the model if users choose poor passphrases.

Recommended approach: device-based recovery for Phase 1, optional recovery passphrases for Phase 2.

## Attachments

Attachments are Phase 2. Files must be encrypted before upload, metadata must be encrypted, and download URLs must never imply plaintext access. Thumbnail generation must happen on device unless a future trusted processing model is explicitly designed.

## Logging And Analytics Rules

- Never log plaintext prayer content.
- Never log plaintext personal prayer content or routine custom text.
- Never log plaintext group keys or private keys.
- Never send prayer content, personal prayer content, or routine text to crash reporting, analytics, or performance traces.
- Never derive analytics from decrypted prayer or routine text.
- Redact encrypted payload fields from verbose debug logs where practical.
